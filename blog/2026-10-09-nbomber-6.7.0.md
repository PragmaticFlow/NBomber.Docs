## Scenario without Response

When a scenario has no steps, the scenario `Response` is the only result that NBomber gets for each iteration. You can set the status code and the size, and you can mark the iteration as failed.

```csharp
var scenario = Scenario.Create("http_scenario", async context =>
{
    var response = await httpClient.GetAsync("https://nbomber.com");

    return response.IsSuccessStatusCode
        ? Response.Ok(statusCode: response.StatusCode.ToString())
        : Response.Fail(statusCode: response.StatusCode.ToString());
});
```

When a scenario has a multiple steps, the situation is different. Each `Step` returns its own `Response`, and NBomber measures each `Step` separately. The final `return Response.Ok();` at the end of the scenario does not add any information. It is boilerplate.

```csharp
var scenario = Scenario.Create("my e-commerce scenario", async context =>
{
    await Step.Run("login", context, async () => 
    { 
        return Response.Ok();
    });    

    await Step.Run("logout", context, async () => 
    {
        return Response.Ok();
    });

    // highlight-start
    return Response.Ok();
    // highlight-end
});
```

In this release, `Scenario.Create` has a new overload. The scenario function can now return a plain `Task`, without a `Response`. In this case, NBomber treats the iteration as successful (as if you returned `Response.Ok()`).

```csharp
var scenario = Scenario.Create("my e-commerce scenario", async context =>
{
    await Step.Run("login", context, async () => 
    { 
        return Response.Ok();
    });    

    await Step.Run("logout", context, async () => 
    {
        return Response.Ok();
    });
});
```

## Tags

When you run the same load test against different environments, regions or builds, it is difficult to tell the results apart. In this release, NBomber adds **Tags**: key/value pairs that you attach to a test run or to a scenario. You can use them to filter and group your results in reports, reporting sinks and dashboards.

There are two levels of tags:

- **Session (global) tags** describe the whole test run, for example `env=prod` or `region=eu`.
- **Scenario tags** describe one scenario, for example `team=payments` or `service=billing`.

### Adding tags via code

```csharp
var scenario = Scenario.Create("payment_scenario", async context =>
{
    // ...
    return Response.Ok();
})
// highlight-start
.WithTags(("team", "payments"), ("service", "billing"));
// highlight-end

NBomberRunner
    .RegisterScenarios(scenario)
    // highlight-start
    .WithTags(("env", "prod"), ("region", "eu"))
    // highlight-end
    .Run();
```

You can also set tags without changes to your code, with the JSON config or the `--tags` CLI argument. For more information, see the [Tags](/docs/nbomber/tags) page.

## Custom Warmup Simulations

Before the main load test starts, NBomber runs a warm-up phase. The warm-up gives the target system time to fill caches, compile code (JIT) and open connections. NBomber does not include warm-up results in the final report.

Before this release, the warm-up used the same load simulations as the main test, cut short by `WarmUpDuration`. This causes a problem for high-load tests. If the main load is 500 requests per second, the warm-up also sends 500 requests per second to a cold system. The cold system can return errors or timeouts before the real measurement starts.

```csharp
var scenario = Scenario.Create("http_scenario", async context =>
{
    // ...
    return Response.Ok();
})
// the warm-up runs Inject(500 RPS) for 30 seconds
.WithWarmUpDuration(TimeSpan.FromSeconds(30))
.WithLoadSimulations(
    Simulation.Inject(rate: 500, interval: TimeSpan.FromSeconds(1), during: TimeSpan.FromMinutes(5))
);
```

In this release, you can give the warm-up phase its own load profile. Use the new `WithWarmUpSimulations` method. In the example below, the warm-up increases the load slowly from 0 to 500 requests per second. Then the main test starts at the full rate.

```csharp
var scenario = Scenario.Create("http_scenario", async context =>
{
    // ...
    return Response.Ok();
})
// highlight-start
.WithWarmUpSimulations(
    Simulation.RampingInject(rate: 500, interval: TimeSpan.FromSeconds(1), during: TimeSpan.FromSeconds(30))
)
// highlight-end
.WithLoadSimulations(
    Simulation.Inject(rate: 500, interval: TimeSpan.FromSeconds(1), during: TimeSpan.FromMinutes(5))
);
```

Rules:

- The warm-up phase runs the warm-up simulations for their full planned duration. In the example above, the duration is 30 seconds.
- If you set warm-up simulations, NBomber ignores `WarmUpDuration`. If you set both, NBomber logs a warning.
- `WithoutWarmUp()` disables the warm-up phase, and also removes the warm-up simulations.

You can also set warm-up simulations without changes to your code, with the `WarmUpSimulationsSettings` field in the [JSON config](/docs/nbomber/json-config). For more information, see the [Scenario WarmUp](/docs/nbomber/scenario#scenario-warmup) page.

## Cluster fix: waiting issues on discovery phase

Before this release, NBomber Cluster nodes waited forever in some failure cases. If the NATS server was not available, if the NATS URL was wrong, or if the Coordinator and the Agents used different `ClusterId` values, the nodes did not stop. They retried again and again, and in a CI/CD pipeline, the job did not stop until the pipeline timeout.

In this release, NBomber adds missed timeouts for these cases. When a timeout occurs, the node stops.

- **NATS connection.** The Coordinator and the Agents try to connect to the NATS server for 1 minute. If the connection fails, the node stops with this error:

> Couldn't connect to NATS server: 'nats://localhost' during 00:01:00. Please check that NATS is running and that the NATS URL is correct.

- **Agent discovery.** The Coordinator waits 1 minute for the required number of Agents (`AgentsCount`). If not enough Agents are available, the Coordinator stops with this error:

> Coordinator couldn't establish the cluster: required AgentsCount: 3, available agents: 1. Please check that all Agents are running with the same ClusterId.

- **Agent idle wait.** An Agent waits 1 minute for the first command from the Coordinator. If no command arrives, the Agent stops with this error:

> Agent didn't receive any command from the Coordinator during 00:01:00. Please check that the Coordinator is running with the same ClusterId. The Agent is stopping.

For more information about the cluster setup, see the [Cluster](/docs/cluster/overview) page.

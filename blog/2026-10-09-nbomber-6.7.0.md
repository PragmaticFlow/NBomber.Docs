NBomber 6.7.0 is here! Our team has been hard-working on this release, and I genuinely hope you’ll find it useful. This post will be about NBomber updates and the next one will be about NBomber Studio. Let’s jump in and take a look at the highlights.

## Scenario without Response

If a scenario has no steps, the scenario `Response` is the only result NBomber gets for each iteration. You can set the status code and payload size, and you can mark the iteration as failed.

```csharp
var scenario = Scenario.Create("http_scenario", async context =>
{
    var response = await httpClient.GetAsync("https://nbomber.com");

    return response.IsSuccessStatusCode
        ? Response.Ok(statusCode: response.StatusCode.ToString())
        : Response.Fail(statusCode: response.StatusCode.ToString());
});
```

When a scenario has multiple steps, the behavior is a little different. Each `Step` returns its own `Response`, and NBomber measures every step separately. The final `return Response.Ok();` at the end of the scenario adds no real information—it is just boilerplate.

```csharp
var scenario = Scenario.Create("my e-commerce scenario", async context =>
{
    await Step.Run("login", context, async () => 
    { 
        return Response.Ok();
    });    

    await Step.Run("logout", context, async () => 
    {
        return Response.Ok();
    });

    // highlight-start
    return Response.Ok();
    // highlight-end
});
```

In this release, `Scenario.Create` got a new overload. The scenario function can now return a plain `Task` without a `Response`. In that case, NBomber treats the iteration as successful, just like it would with `Response.Ok()`.

```csharp
var scenario = Scenario.Create("my e-commerce scenario", async context =>
{
    await Step.Run("login", context, async () => 
    { 
        return Response.Ok();
    });    

    await Step.Run("logout", context, async () => 
    {
        return Response.Ok();
    });
});
```

## Custom Warmup Simulations

Before the main load test starts, NBomber runs a warm-up phase. This gives the target system time to fill caches, JIT-compile code, and open connections. Warm-up results are excluded from the final report.

Before this release, the warm-up used the same load simulation as the main test, just shortened by `WarmUpDuration`. That creates a problem in high-load scenarios. If the main test is sending 500 requests per second, the warm-up phase also hits a cold system with the same rate. The system may return errors or time out before the real measurement begins.

```csharp
var scenario = Scenario.Create("http_scenario", async context =>
{
    // ...
    return Response.Ok();
})
// the warm-up runs Inject(500 RPS) for 30 seconds
.WithWarmUpDuration(TimeSpan.FromSeconds(30))
.WithLoadSimulations(
    Simulation.Inject(rate: 500, interval: TimeSpan.FromSeconds(1), during: TimeSpan.FromMinutes(5))
);
```

In this release, you can give the warm-up phase its own load profile. Use the new `WithWarmUpSimulations` method. In the example below, the warm-up increases the load gradually from 0 to 500 requests per second, and only then does the main test start at full speed.

```csharp
var scenario = Scenario.Create("http_scenario", async context =>
{
    // ...
    return Response.Ok();
})
// highlight-start
.WithWarmUpSimulations(
    Simulation.RampingInject(rate: 500, interval: TimeSpan.FromSeconds(1), during: TimeSpan.FromSeconds(30))
)
// highlight-end
.WithLoadSimulations(
    Simulation.Inject(rate: 500, interval: TimeSpan.FromSeconds(1), during: TimeSpan.FromMinutes(5))
);
```

A few rules to keep in mind:

- The warm-up phase runs the warm-up simulations for their full planned duration. In the example above, that means 30 seconds.
- If you set warm-up simulations, NBomber ignores `WarmUpDuration`. If you set both, NBomber logs a warning.
- `WithoutWarmUp()` disables the warm-up phase and removes the warm-up simulations as well.

You can also configure warm-up simulations without changing your code by using the `WarmUpSimulationsSettings` field in the [JSON config](/docs/nbomber/json-config). For more details, see the [Scenario WarmUp](/docs/nbomber/scenario#scenario-warmup) page.

## Tags

When you run the same load test against different environments, regions, or builds, it is hard to tell the results apart. In this release, NBomber adds **Tags**: key/value pairs you attach to a test run or a scenario. You can use them to filter and group results in reports, reporting sinks, and dashboards.

There are two levels of tags:

- **Session (global) tags** describe the whole test run, for example `env=prod` or `region=eu`.
- **Scenario tags** describe a single scenario, for example `team=payments` or `service=billing`.

### Adding tags via code

```csharp
var scenario = Scenario.Create("payment_scenario", async context =>
{
    // ...
    return Response.Ok();
})
// highlight-start
.WithTags(("team", "payments"), ("service", "billing"));
// highlight-end

NBomberRunner
    .RegisterScenarios(scenario)
    // highlight-start
    .WithTags(("env", "prod"), ("region", "eu"))
    // highlight-end
    .Run();
```

You can also add tags without changing your code by using the JSON config or the `--tags` CLI argument. For more information, see the [Tags](/docs/nbomber/tags) page.

## Reporting Sinks: Data Transfer and Tags

In this release, we updated all the official reporting sinks: [InfluxDB](/docs/reporting/realtime/influx-db), [TimescaleDB](/docs/reporting/realtime/timescale), [Datadog](/docs/reporting/realtime/datadog), and [OpenTelemetry](/docs/reporting/realtime/opentelemetry). These sinks now write the new data transfer metric, the tags, and the status codes for each step. To get the latest behavior, update your sink packages to the newest versions.

### Tags

The sinks merge the session tags and the scenario tags and add them to every data point.

```csharp
var influxDbSink = new InfluxDBSink();

var scenario = Scenario.Create("payment_scenario", async context =>
{
    // ...
    return Response.Ok();
})
.WithTags(("team", "payments"), ("service", "billing"));

NBomberRunner
    .RegisterScenarios(scenario)
    .WithTags(("env", "prod"), ("region", "eu"))
    .WithReportingSinks(influxDbSink)
    .LoadInfraConfig("infra-config.json")
    .Run();
```

In this example, each data point for `payment_scenario` includes the tags `env=prod`, `region=eu`, `team=payments`, and `service=billing`. In Grafana, Datadog, or any OpenTelemetry backend, you can use these tags to filter and group metrics. For example, you can compare `env=staging` with `env=prod` on the same dashboard.

### Status codes per step

Before this release, the InfluxDB, Datadog, and OpenTelemetry sinks wrote status codes only for the scenario. Now they write status codes for each step using the `step` tag. That makes it much easier to see which step is returning errors, such as `500` or `timeout`, in your dashboards.

## CSV report: simulation name and value

The CSV report is handy when you want to process test results with your own tools—for example, Excel, a Python script, or a database. Before this release, the CSV report did not show the load simulation used by the scenario. If you ran the same scenario with different loads, such as when testing the maximum RPS your system can handle, you had to record that information separately.

In this release, the CSV report includes two new columns:

- `simulation_name`: the name of the load simulation, for example `inject`, `keep_constant`, or `ramping_inject`.
- `simulation_value`: the load value. For open simulations, this is the rate. For closed simulations, it is the number of copies (virtual users).

## Cluster fixes: infinite waiting

Before this release, NBomber Cluster nodes could wait forever in some failure scenarios. If an Agent did not receive commands from the Coordinator node, it stayed stuck indefinitely. The same was true when the NATS server was unavailable or when the Coordinator and Agents used different `ClusterId` values. In those cases, the nodes kept retrying, and a CI/CD job could remain stuck until the pipeline timed out.

This release fixes those issues by adding the missing timeouts.
